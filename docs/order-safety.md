# 订单 ID 与数据库重复保护

本次对应 `todolist.md` 的前两个 P0：订单 ID 时间戳计算、数据库兜底防重复订单。保留现有 Redis 预占、用户锁、应用查重和 MQ 消费策略。

## 订单 ID 修复

旧代码 `timestamp = nowSecond = BEGIN_TIMESTAMP` 把时间高位固定成起始时间戳；日期计数器重新从 1 开始时可能与历史 ID 重复。现在从一次 `Instant` 获取 epoch 秒与 UTC 日期桶，正确计算秒差。

编码保持一个正 `long`：1 位符号位、31 位时间差、32 位日序列。时间差必须处于 `0..Integer.MAX_VALUE`，序列必须处于 `1..4294967295`；超范围或 Redis 不可用时拒绝发号，不降级为本地计数。公共方法仍为 `nextId(String)`，固定时钟重载只供同包测试使用。

所有实例必须使用同一个发号 Redis 数据集。序列键继续采用 `icr:order:yyyy:MM:dd`，日期按 UTC 计算，不新增过期时间，也不主动重置已有计数。业务缓存清理不得删除、淘汰或回滚这些键；发号所依赖的 Redis 应满足所需的持久化和保留要求。应用正常重启不重建已存在的计数。

### 计数丢失后的处理约束

修正时间差不等于解决任意 Redis 数据丢失。计数键丢失后 `INCR` 会从 1 开始；本补丁没有自动发现和修复该事件的机制。

1. 发现计数被删除、淘汰或恢复到落后备份时，先停止所有订单发号入口，避免继续以错误计数运行。
2. 恢复可信的持久化数据，并核对数据库订单、已受理但未落库的消息和发号记录。只看数据库最大 ID 不足以证明恢复完整；备份也可能落后于已返回给用户的 ID。
3. 已有可靠证据确定相关 UTC 日期桶曾发出的最大序列时，维护期间把计数恢复到不低于该值，再验证时钟和实例连接后恢复发号。不要一边发号一边人工修改计数。
4. 无法确认完整序列时继续停发；可以在确认从未发号的新 UTC 日期到来后、核实时钟及历史／在途发号范围后启用新的日桶。不能靠随意换 Redis key 前缀宣称 ID 已安全，因为前缀不进入 ID 位编码。

旧版本生成的 ID 没有正确编码创建时间，不能用新算法解码其日期。历史 ID 不重写；新 ID 的数值也不保证大于全部旧 ID，跨版本记录按明确的创建时间等业务字段排序。

历史 ID 若一直保留到 `2074-01-01T00:00:00Z`，该秒的新时间差会等于旧算法固定高位 `1640995200`；相同低位序列存在跨版本碰撞窗口。本次不改未来秒的编码规则，记录为后续兼容边界，届时需提前采取保留该秒／拒绝发号等处理，不能宣称当前方案对无限保留的历史 ID 永久无碰撞。

## 数据库唯一约束

`tb_voucher_order` 增加唯一键 `uk_order_user_voucher(user_id, voucher_id)`。同一用户和同一券只能保留一条订单记录，包括已取消／已退款记录；若未来允许取消后重领，需要另行调整业务与约束模型。

保留应用层用户锁与查重。数据库库存扣减与插入订单继续处于同一个事务；插入异常向外传播，保存返回 `false` 也抛出运行时异常，避免扣库存单独提交。不在事务方法内捕获唯一键异常后直接正常返回，也不把主键碰撞一概当成重复领取吞掉。

### 新建数据库

按原方式执行 `src/main/resources/db/smart-life.sql`，新表已包含该唯一键。

### 已有数据库：一次性迁移

先备份并暂停订单写入，用维护账户连接明确的目标数据库。应用不会自动执行 ALTER。

```sql
-- 先查看已有索引；如果已经存在相同组合的唯一约束，核对后无需重复执行。
SHOW INDEX FROM tb_voucher_order;

-- 执行迁移文件前，检查是否存在重复组合。
SELECT user_id, voucher_id, COUNT(*) AS duplicate_count
FROM tb_voucher_order
GROUP BY user_id, voucher_id
HAVING COUNT(*) > 1;
```

若有重复，先核对有效订单、支付状态和库存，再制定修复方案；本迁移不自动选订单、不删除或合并记录。核对完毕后，在 MySQL 客户端执行：

```sql
SOURCE /absolute/path/to/smart-life/src/main/resources/db/migrations/2026-11-08-order-user-voucher-unique.sql;
```

脚本再次报告重复，再建立唯一约束。MySQL 在建索引时发现重复会拒绝操作，原记录保留。客户端不要使用 `--force` 跳过错误。迁移只执行一次；已安装同名索引后重跑会报告索引已存在。

完成后检查 `SHOW INDEX` 中该索引为唯一索引，列顺序为 `user_id`、`voucher_id`。可用隔离环境验证不同订单 ID 的同用户同券插入被拒绝，其他用户／其他券仍可插入。

## 验证命令

先按 [本地开发](local-development.md) 配好专用 MySQL、Redis、RocketMQ，设置 `SMARTLIFE_INTEGRATION_TESTS=true` 及专用连接参数；旧开发卷先执行上述迁移。

```bash
# 无需外部服务：含固定时钟及保存失败单元回归。
mvn clean verify

# 专用测试服务：原链路、数据库唯一约束／迁移、真实 Redis／独立 JVM 发号。
mvn -Dtest=StackUpgradeIT,OrderSafetyIT,RedisIdWorkerIT test

# 前端检查，保留原有脚本与模板验证。
npm run check:frontend
```

迁移集成测试使用连接局部的 `TEMPORARY` 旧结构订单表，显式 `DROP TEMPORARY` 清理，不删除真实订单表。其他案例仅清理自己创建的虚构券、订单和测试前缀计数。

数据库事务回滚只恢复 MySQL 修改，不会自动恢复 Redis 预占。锁失败的 MQ 确认语义、消息发送超时、库存补偿幂等、支付／取消／退款仍是各自的待办，不将本次两个修复描述为完整订单可靠性闭环。
