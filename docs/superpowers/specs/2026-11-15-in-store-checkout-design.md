# Smart Life 到店买单与优惠结算设计

日期：2026-11-15。状态：独立设计审查通过，用户已回复“按这套规则实现（推荐）”，进入实现及验证。用户已选到店买单方案，未选商品购物车；本文件中的具体默认规则是经用户确认的项目规则，不冒充美团内部算法。

## 目的、范围和实施次序

把原有“买代金券→模拟支付→到店核销”扩展为“确认消费账单→选择优惠→服务端试算→确认模拟补付并核销”。优先复用当前商户详情、个人页订单面板、权限和SQL事务；保留历史订单快照、MQ受理、批量发券和原核销流程。

本阶段交付到店消费账单、满减/折扣、已购代金券抵扣、有限组合择优、全额账单撤销、规则管理及一致性验证。钱仍是模拟，没有支付网关、真实POS、佣金清算、商品/SKU/购物车或真实平台接口。部分消费退款需要消费项目/分摊规则，明确拒绝请求，不伪装为已支持。

五项暂缓内容拆成可独立验收的阶段：

1. 本设计先解决“没有账单、没有优惠规则”的前提，完成结算和可验证的组合子集。
2. 以新增规则读取为实际负载，测量后独立决定模板缓存，历史券快照不进长期动态缓存。
3. 批量导入独立worker先定义重启不影响在线请求、任务可恢复和相同资源预算的目标，单独设计验证。
4. 分片是明确的架构实验，单独解决库存事务、唯一约束、商户跨片查询、迁移回退；不能以本设计获批代替分片方案审查。

不通过改文字把五项全部勾选；结算实测后可勾对应到店范围，组合项原有“部分退款”验收仍未实现时保留未勾选并列明已完成子项。

## 方案及选择依据

- 用户已选：到店消费账单，适合现有商户券和核销，金额由商户确认，优惠选择由顾客确认。
- 未选：商品购物车。适用商品、订单行及逐项退款需要新的商品交易模型，本轮没有这个需求。
- 实现采用当前单体内的专用计算器和SQL事务。外置规则引擎/结算微服务会增加规则发布、远程失败和事务边界，当前没有相应收益，暂不引入。

## 用户及页面流程

1. 顾客在原商户详情进入“到店买单”弹窗，填消费总额及不参与优惠金额，保存本人草稿。商户来自当前页面，后台校验商户存在；所有金额仍待商户确认，草稿不能支付。
2. 现有个人页商户区增加“查消费账单”选项，按账单号查本店账单。当前授权店主/管理员确认或修改金额，后台保存金额版本，进入CONFIRMED。无需输入任意客户身份或增设客户搜索接口。
3. 顾客从原订单面板切换“消费账单”列表，查看商户确认的金额，选择本人已支付且可使用的本店代金券（最多一张，默认不选择），以及自动择优或手选免费优惠，得到服务端报价。
4. 报价明确列出原消费、不参与优惠、各步门槛基数/优惠、代金券购入成本/本次抵扣、未使用面值、本次补付及累计现金成本。最终按钮写“确认模拟补付并核销”，零补付也必须确认。
5. 支付成功在同一数据库事务中完成账单结算与券核销；网络超时通过原账单列表刷新查询，不能直接当失败或再次生成新账单。
6. 商户在同一详情弹窗可撤销已结账单，注明原因；顾客可查看撤销结果。既有直接核销保留，使用同一券行锁，因此和账单结算不能双重消费。

新增账单实体是因为购券订单与线下消费是两笔不同交易，不能复用券订单的status/pay_value来表示两者；新增交互只扩展原页面的弹窗/列表。

## 金额和优惠规则（本项目默认建议）

金额一律整数分；输入范围总额1..100000000分，不参与优惠金额0..总额；折扣为1..9999基点，表示需付比例，例如9000=九折。计算使用long受检运算，拒绝非整数/负数/溢出。数据库及期限为UTC，界面用现有时区规则。

设T为总额、N为不参与优惠金额、E=T-N。严格按以下顺序计算，不对N打折：

1. 门店促销最多一项：满减或折扣。满减以E达门槛时减固定金额、封顶E；折扣需E达门槛，`优惠=floor(E*(10000-需付基点)/10000)`，有上限则再封顶。扣减后余额为E1。
2. 用户明确选择的已购代金券最多一张，必须属于本人、商户一致、快照有效、状态2且在使用期。使用门槛/与促销是否可叠加必须明示：新券创建时支持快照规则；迁移历史券保留原直接核销，缺失明确规则时不允许默默参加新买单，页面说明“此历史券仅支持原核销流程”。
3. 代金券抵扣D不超过E1；不找零，未用面值明确展示，用户确认后整张核销。新券规则包含最低可优惠消费额（以E1判定）、是否可同门店/平台优惠使用。扣减后E2=E1-D。原购券价P只用于说明累计成本，不作为本次再次收费。
4. 平台抵用券最多一张：是单独发给用户的免费权益，不使用付费券订单冒充免费券。满减门槛以E2判断，抵扣不超过E2；使用平台券时账单最低补付1分（若N已覆盖则不用额外保留），无平台券允许补付0分。得到平台优惠F。
5. 本次补付=N+E2-F。累计现金成本=P+本次补付（未选已购券则P=0），相对原消费的现金节省为T-累计成本，可能为负，不能伪称始终优惠。

规则结构为有类型校验的字段：类型、门槛、满减金额/折扣基点、封顶金额、有效期、优先级、版本及与另外两类是否允许叠加。每次规则变更生成新版本。启用门店促销最多20项，用户有效平台券最多20项；已用但未过期/未撤销的平台权益继续占用发放额度，为账单撤销恢复预留位置，过期/撤销后释放。超过配置上限明确拒绝创建/发放，不悄悄截断择优结果。封顶仅用于折扣，满减请求的cap必须为0，避免填写后被忽略。仅管理员能发平台券，店主只能管理本店促销/本店付费券规则。平台券默认按明确店铺范围发放，禁止空范围被当作全店通用；首版单店，不实现全平台券。

自动择优只枚举免费门店促销/平台券及“不使用”组合（最多21×21）；代金券由用户指定，保持固定。仅允许双方声明兼容的组合，逐步校验门槛和时间。目标为当前补付最少；平局依次按门店优先级降序、平台优先级降序、平台券较早到期、门店规则ID及平台券ID升序排序，形成总序，无对应候选的优先级按0、日期/ID排在最后。单步优惠或抵扣为0的候选自动排除，手选则明确拒绝，不得消耗无收益的权益；全不参与优惠时只能原价支付。报价同时返回可选及不可用原因。用户手选不合法组合明确报错，不能静默换券。

示例（独立场景）：

| 场景 | 结果 |
| --- | --- |
| T=18000,N=2000，已购价8000/面值10000，无其他优惠 | E=16000,D=10000，本次8000，累计16000，现金省2000 |
| T=18000,N=2000，门店满15000减2000，不选代金券 | 满减门槛16000达标，本次16000 |
| T=18000,N=2000，允许满减+上述代金券 | 门店优惠2000,E1=14000,D=10000，本次6000，累计14000 |
| 上一场景再选“满5000减1000”平台券 | E2=4000不达门槛，拒绝/自动择优不选，不能按18000判断达标 |
| E=101，九折，无其他优惠 | 优惠10，本次91（优惠向下取整，不产生半分） |
| T=100,N=0，平台优惠100 | 平台券最多抵99，本次1 |

## 数据及状态

新增表均纳入初始DDL和旧库增量迁移；不改变旧订单金额或状态：

- `tb_checkout_bill`：全局ID、owner_user_id、shop_id、request_key及创建负载指纹、金额、amount_version、state、确认人/时间、报价版本/JSON/截止时间、最终快照JSON及pay/reverse时间。唯一(owner,request_key)。状态DRAFT→CONFIRMED→PAID→REVERSED；未支付可由本人取消进入CANCELLED。报价存在于CONFIRMED状态，不等于结算。账单确认后15分钟支付期限，过期成为CANCELLED；不占券不退库存。
- `tb_checkout_promotion`：店铺、MERCHANT类型、FULL_REDUCTION或DISCOUNT、规则字段及version/active。平台券模板也使用此表的PLATFORM类型，仅管理员写；每次修改在同一事务递增版本和店铺规则集epoch。epoch存于`tb_shop.checkout_rule_version`新增非负BIGINT列，默认0；无需独立版本表。规则写入先锁该商户行再改促销，结算锁同一行后读取规则快照。
- `tb_checkout_coupon`：平台权益ID、模板ID、owner、发放幂等键、发放时完整规则快照、有效期、used_bill_id；不直接修改已发放权益规则，撤销仅对未用权益生效。唯一(owner,发放幂等键)。
- `tb_checkout_voucher_use`：order_id主键、bill_id及核销时间，表示当前绑定；结算同事务创建，撤销时删除。历史使用不依赖该表保留，永久存在于原账单不可改的结算/撤销快照及审计中。
- `tb_checkout_reversal`：bill_id唯一、操作者、原因、补付款模拟退额、返回的券ID与结果/时间。全额账单撤销最多一次。
- 新付费券的结算适用字段保存在券模板并在`tb_order_lifecycle`捕获完整快照；历史空值不猜测规则。不靠当前券模板重写已购券合同。创建表单新增“到店买单适用”及门槛/叠加项，默认关闭，保持旧客户端行为；启用后必须经消费账单结算使用，原直接`redeem`接口明确拒绝该类券并提示走买单，不能绕过最低消费/叠加条件。旧券仍用原直接核销，不强制历史迁移。

金额确认、报价和支付都以数据库账单为准；客户端不能提交可信owner/price/discount。所有long ID沿用字符串序列化，列表采用现有稳定游标，limit1..50。可选已购券按订单ID稳定游标分页，每页50，原弹窗提供加载更多，不能用前50张遮住较早合法券。权限异常对非本人/非管理商户统一不泄露对象存在性。

## 报价、版本及事务边界

每次试算只保存一份账单当前报价：随机quote token、amount_version、已选券ID、所用门店规则版本/店铺epoch、完整计算结果及数据库时间后120秒截止；替换报价使旧token失效。规则、金额和权限均不能仅由缓存决定。读取失败不支付。

提交由本人提供账单ID和quote token，在SQL事务中先锁账单、所选券订单（ID升序）、平台权益（ID升序）、规则集版本行；锁定后读取DB时间。重新校验本人/商户、账单状态/金额版本、支付期限/报价期、券状态/期限、规则变更/撤销及叠加，重算金额和版本必须与已确认报价一致；不一致返回“报价已更新，请重新确认”，不自动按新价扣款。

结算将账单置PAID、付费券2→3并写`use_time`及当前绑定、平台权益写used_bill_id、不可变结算快照在一个本地事务提交。任何失败全部回滚。已有直接核销、退款同样锁券订单；防止一券两单和核销/退款竞态。行锁等待后重读时间；死锁/瞬时失败回滚并可用原token重试。已PAID账单仅在token与成功快照一致时返回原结果，别的token拒绝，不能重复扣款或消耗权益。

金额修改只能在未支付状态由当前授权商户操作，递增amount_version、清空报价，并重新计支付截止。本人取消/超时取消与支付共享账单行锁。规则发布/停用与结算共享相同店铺epoch锁，避免“检查版本后被改规则”的窗口；已发放平台券按快照使用，撤销与使用锁同一权益行。

## 全额消费账单撤销

商户必须有当前权限，锁账单→绑定券订单→平台权益，验证原结算绑定仍一致。只允许PAID→REVERSED；同时记录唯一撤销行、模拟退回**本次补付款**，恢复本账单核销的代金券3→2/清use_time及当前绑定，释放本账单使用的平台权益。券期限不延长，过期就保持不可用；返回与不可用原因均展示。

不退购券价、不退券面值、不修改已发生的门店优惠成现金。恢复后的代金券若满足原未用券退款条件，可由原退款接口另行申请退购券款。原券订单一人一券资格及库存不因账单撤销变化。平台权益若已过期或被撤销，释放消费占用不等于重新变有效。重复撤销返回原结果；部分金额请求拒绝，不修改账单、券或模拟资金。

## 缓存与架构后续的解阻目标

新增公开规则列表是可测的模板读取入口。基线记录同店重复请求的SQL次数/P95及规则数量，再评估复用现有Redis缓存工具；若采用缓存，仅展示/候选用短TTL，提交锁SQL重算，权限/已购快照/权益消费状态不长期缓存。对比冷/热读取、规则更新、Redis不可用及并发更新；未测出收益就独立记录不引入的结论，不写成完成模板缓存。

独立worker后续须做到后台更新/退出不影响在线进程服务，私有文件持久化与解析失败可解释、租约可重领；资源总预算和数据库连接预算固定比较，不能多开JVM当免费性能提升。

分片后续须比较相同CPU/内存预算下索引优化的单库与分片，并先解决按券扣库存与按用户分订单的跨库事务。需提交明确路由、唯一约束、库存一致性、订单号查询、商户分页、迁移校验和回退设计。先前压测只证明局部压力，未证明必须分片。
