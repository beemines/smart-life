# P2 voucher distribution design

User approved implementation after five-item review and selected: batch creates unpaid voucher orders; recipients pay before use. Keep lifetime one-user-one-voucher, cancellation/refund retains eligibility. Reuse existing modules/pages, test backend and actual frontend before push, final-head all CI green and screenshots committed. Existing checkout/IDEA paths retained on feature branch, matching established workflow.

## Approach and scope
Selected reuse paid voucher ordering (user choice), rather than free grants requiring distinct funds/refund rules. Extend existing controller/service/JDBC/MySQL/Redis/RocketMQ; no new page, services, or generic job framework. Focused persistent task and row records provide restartable ingestion and dispatch. Excel uses Apache POI 6.0.0 event parsing, bounded input and batches; official release/API docs were read before implementation. Only xlsx, one sheet, single userId column with text IDs preferred. Formula/ambiguous numeric IDs invalid; invalid and duplicate rows retain original row numbers. Bound compressed file5MiB, rows10000, cells/text lengths, ZIP expansion. Import must not dispatch until fully validated/ready; malformed upload cannot leave a dispatchable partial task. Batch size100, persisted recoverable processing, scheduler default true but disabled integration fixtures.

Task records: owner merchant via voucher's persisted shop, creator, client request key, voucher, state (IMPORTING/READY/RUNNING/COMPLETED/PARTIAL/IMPORT_FAILED), import error; counts aggregated from rows. Row records: task,row number, recipient text/parsed userId, stable business orderId/requestKey, state READY/PROCESSING/SUCCEEDED/FAILED, retryable, attempts,last_attempt_at,error. Unique task+row and task+target user processing identity; duplicate input rows must be visible but not issued. Task creation idempotency scoped operator+key, rejects same key/different voucher or payload. No file/path/token in public replies. IDs always response strings.

Per row validate real recipient exists, voucher is active seckill/READY and within claim window; explicitly authorized merchant only can submit/list/read/retry. Batch invokes an explicit recipient-aware ordering method; never impersonate target with UserHolder. Stable accepted intent+Redis reservation+existing MQ order consumer supply exactly-once effect. Persist relation before sending, uncertain sends retain original ID; after consume observe actual CREATED order as success, permanent rejection as FAILED, pending as PROCESSING. Catch per-row transient failure and cool down, bounded fair scans; restart and multi-instance race safe using durable state and existing order locks. Do not hold SQL locks during Redis/MQ networking. Manual retry only failed retryable rows; permanent invalid/duplicate/already received not retried. Task counts derive committed rows and survive restart; pending is not success.

## Fixed API contract
All Result envelope. Base /voucher/batches. POST JSON {voucherId:string,requestKey:string,userIds:string[]} (max1000); POST /import multipart fields voucherId,requestKey,file; GET ?beforeId=&limit= returns {items,hasMore,nextId}; GET /{id}?beforeRow=&limit= returns {task,items,hasMore,nextRow}; POST /{id}/retry. Task fields id,voucherId,shopId,state,total,ready,processing,succeeded,failed,retryableFailed,error,createdAt. Row fields rowNumber,userId,orderId,state,retryable,attempts,error. GET /shops? not added: user supplies voucher ID, backend checks real persisted shop. Response IDs strings; frontend holds strings. Scheduler and testable public recover entry process ready tasks; no public unauthenticated execute endpoint.

UI: existing order panel's merchant section gains batch submit (voucher ID, newline recipient IDs, xlsx upload), list task summaries, inline details with row pagination, refresh and retryable-only action. Explain recipients pay, no real money and one-person-one-voucher. Busy guards, authoritative refresh and errors; preserve input across temporary errors. Existing ordinary users never see controls but backend is authority.

## Existing list / pricing
Reuse mine cursor/status queries and immutable snapshot. Use query plans at synthetic scale to decide indexes; add user/time/id and user/status/time/id only if demonstrated. No speculative template cache when order snapshots already avoid reading templates. Existing server-owned snapshot quote and payment behavior remain fixed-price voucher purchase; add tests for changed template/client amount tampering if absent. Do not label this as product-cart full-discount settlement. P2 row must accurately retain deferred advanced settlement/cache scope.

## Acceptance
Mixed valid/invalid/duplicate recipients gives durable per-row outcomes/counts. Same key repeat and same MQ/business ID replay no duplicate stock/order; partial exit/recovery reuses original IDs, final results queryable. Cross-shop unauthorized and foreign task reads denied; target absent permanent failure. Xlsx streamed with bounded row buffers, header/schema errors no dispatch, malformed/oversized/too-many rows safe, memory report at increasing sizes rather than claimed linear-free memory. Actual merchant UI import/details/refresh/retry and recipient existing order list/pay verified at desktop/mobile, before/after screenshots. Full prior tests + new tests, exact final-head CI green before finish. Only mark verified todolist scope; preserve before cells and clarify P1 work already exists.
